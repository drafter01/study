## 1. 왜 휴리스틱인가
- UX 디자이너가 가장 익숙한 평가 도구가 휴리스틱(Nielsen 10)이라, "UX 디자이너가 만든 도구"라는 정체성이 형식에서 바로 드러남 (30번)
- 휴리스틱은 **해결책이 아니라 점검 기준**이라서 "전술이 아닌 원칙·핵심 질문 수준"이라는 작업 원칙과 맞음
- 디자이너가 아닌 운영자도 쓸 수 있음: 점검 질문은 누구나 겹, 심각도 평가와 개선 실험은 디자이너 겹 (23번 두 겹 구조)
- 방법론 근거 후보
  - Nielsen(1994)은 사용성 문제 249개를 분석해 10개 휴리스틱을 도출함 → 우리는 발견 123개를 종합해 도출 (원문 확인)
  - Quiñones, Rusu & Rusu(2018)의 도메인 특화 휴리스틱 개발 방법론(탐색 → 실험 → 기술 → 상관 → 선택 → 명세 → 검증 → 정제) → 24번 8단계, Jabareen(2009)과 비교해 방법 장에 쓸 수 있음 (원문 확인, 16번 목록에 추가 필요)
  - 기존 온라인 커뮤니티 사교성(sociability) 휴리스틱 선행 사례가 있는지 확인 필요 (Preece 계열, 원문 확인)

## 3. 휴리스틱 상세
형식: 설명 / 점검 질문(누구나) / 어기면 보이는 모습(근거) / 잘 될 때 신호 / 설계 긴장 / 디지털 제품과 다른 점

### H1 함께할 이유의 공유
- 설명: 사람들이 왜 모였는지 구성원이 함께 정하고, 모임이 바뀌어도 그 약속이 지켜져야 한다
- 점검 질문
  - 구성원에게 "이 모임은 뭐 하는 곳이에요?"라고 물으면 비슷한 답이 나오는가?
  - 그 이유를 운영자 혼자 정했는가, 함께 정했는가?
  - 모임이 커지거나 사람이 바뀌어도 처음의 약속이 지켜지고 있는가?
- 어기면 보이는 모습: "즐기자"던 약속이 승부 위주로 바뀌자 성실한 회원이 떠남(F082) / 무엇을 할지 정하지 않고 시작해 동상이몽(F087) / 유익이 없으면 참여가 끊김(F097)
- 잘 될 때 신호: 구성원이 목적을 자기 말로 설명함, 목적과 운영의 어긋남에 대한 불만이 적음
- 설계 긴장: 분명한 목적 ↔ 다양한 사람에게 열림 / 즐김 ↔ 성과
- 디지털 제품과 다른 점: 제품의 가치 제안은 만든 쪽이 정하지만, 모임의 이유는 구성원이 함께 만들고 바꾼다

### H2 함께 올 사람
- 설명: 처음 오는 사람이 혼자 용기를 내지 않아도 되도록, 함께 올 사람과 찾아올 길이 있어야 한다
- 점검 질문
  - 지금 구성원들은 처음에 누구와, 어떻게 왔는가?
  - 아는 사람이 하나도 없는 사람은 이 모임을 어떻게 알고, 어떻게 올 수 있는가?
  - "나 같은 사람이 가도 될까"라는 걱정에 답해 주는 것이 있는가?
- 어기면 보이는 모습: 아는 사람 없이 혼자 가는 데 큰 용기가 필요함(F069) / 어디서 찾아야 할지 모름(F072) / 실력이 있어야 받아준다고 여겨 포기(F075) / 40대가 젊은 모임에 끼는 두려움(F011)
- 잘 될 때 신호: 참여자가 다시 다른 사람을 데려옴(F113), 혼자 온 사람의 재방문
- 설계 긴장: 인맥으로 넓히기 ↔ 인맥 없는 사람에게 열기 (F123)
- 디지털 제품과 다른 점: 앱은 혼자 검색해서 들어오지만, 모임은 함께 오는 사람이 첫 장벽을 낮춘다

### H3 첫날의 자리와 몫
- 설명: 처음 온 사람이 혼자 남겨지지 않고, 그날 할 일이 있어야 한다
- 점검 질문
  - 처음 온 사람이 혼자 서 있게 되는 순간은 언제인가?
  - 처음 온 사람도 그날 실제로 참여할 몫이 있는가, 아니면 구경하다 가는가?
  - 처음 온 사람을 맞는 일은 누가 하는가?
- 어기면 보이는 모습: 신입이 경력자에게 순서가 밀려 오래 기다리다 포기(F071) / 회비를 내도 시합에 못 나가 점점 안 나감(F077)
- 잘 될 때 신호: 혼자 있는 사람에게 먼저 말을 거는 문화(F115), 첫 참여 후 재방문, 첫날 대화한 사람 수
- 설계 긴장: 기존 구성원의 편안함과 실력 기준 ↔ 새 사람의 자리
- 디지털 제품과 다른 점: 앱의 온보딩은 화면이 안내하지만, 모임의 온보딩은 다른 구성원이 한다

### H4 의도된 문턱
- 설명: 들어오는 데 요구하는 것은 소속의 의미를 만들 만큼만 있고, 누구를 걸러내는지 알고 있어야 한다
- 점검 질문
  - 들어오고 머무르는 데 무엇(돈, 시간, 과제, 실력, 면접)을 요구하는가?
  - 그 요구가 소속의 의미를 만드는가, 그냥 귀찮은가?
  - 그 요구 때문에 오지 못하는 사람은 누구인가? 그것은 의도한 것인가?
- 어기면 보이는 모습: 경계가 배제의 고통을 만듦(F035) / 실력 기준이 낄 곳이 없다는 느낌을 줌(F075) / 지식·지위 차이로 친해지기 어려움(F010)
- 잘 될 때 신호: 회비와 과제가 참여의 동력이 됨(F003, F004), 들어왔다는 자부심(F099), 진입 단계별 이탈이 의도한 곳에서만 생김
- 설계 긴장: **낮은 문턱 ↔ 의도된 마찰** (프레임워크의 대표 긴장)
- 디지털 제품과 다른 점: 앱은 마찰을 없앨수록 좋지만, 모임에서는 적당한 마찰이 투자와 소속을 만든다. 마찰의 양은 누구를 배제하는가에 대한 윤리적 판단이다

### H5 사람의 반응
- 설명: 누군가 처음 무언가를 했을 때 다른 구성원의 반응이 돌아와야 한다
- 점검 질문
  - 처음 글을 올리거나, 처음 발표하거나, 처음 완주한 사람에게 누가 반응하는가?
  - 반응이 오는 사람과 오지 않는 사람이 정해져 있지 않은가?
  - 그 반응은 진심인가, 형식인가?
- 어기면 보이는 모습: 처음 올린 사진에 아무 반응이 없었음(F106)
- 잘 될 때 신호: 댓글 한 줄이 다음 주 참여 동기(F020), 인정이 쌓여 열정적 참여로(F107), 꼴찌에게도 박수(F116)
- 설계 긴장: 진정한 반응 ↔ 형식적·강요된 반응
- 디지털 제품과 다른 점: 제품은 시스템이 즉시 피드백하지만, 모임의 피드백은 사람이 줘야 해서 늦거나 없을 수 있다
- 메모: 근거가 가장 얇음(자료 4). H3과 합칠지 연구자 결정 필요

### H6 관계가 생기는 상황
- 설명: 서로 말을 걸 핑계가 되는 활동과, 활동이 끝난 뒤 머무를 시간이 있어야 한다
- 점검 질문
  - 처음 만난 사람끼리 자연스럽게 말을 걸 수 있는 활동인가?
  - 활동이 끝난 뒤 바로 흩어지는가, 머무를 시간과 장소가 있는가?
  - 같은 사람을 여러 번 만날 수 있는 구조인가?
- 어기면 보이는 모습: 공통점이 없으면 다시 만나지 않음(F053) / 연습 없이 시합만 하고 헤어지자 흥미가 사라짐(F080) / 사건이 모호하게 끝나면 응집이 약해짐(F038)
- 잘 될 때 신호: 활동 후 남는 사람의 비율, 결석하면 서로 궁금해함(F104), 서로 이름을 아는 정도
- 설계 긴장: 활동 중심 ↔ 친목 중심
- 디지털 제품과 다른 점: 제품은 사용자와 시스템의 상호작용을 설계하지만, 모임은 **사용자와 사용자 사이의 상호작용이 일어날 상황**을 설계한다 ← 논문 중심 주장

### H7 강제 없는 리듬, 고르는 깊이
- 설명: 다시 올 때와 이유는 분명하되 의무는 없고, 얼마나 가까워질지는 스스로 고를 수 있어야 한다
- 점검 질문
  - 다음 모임이 언제인지, 왜 가야 하는지 분명한가?
  - 한 달 빠진 사람이 부담 없이 돌아올 수 있는가?
  - 가볍게 오가는 사람과 깊이 관계 맺고 싶은 사람이 모두 있을 수 있는가?
  - 활동이 매번 똑같아 지루해지고 있지 않은가?
- 어기면 보이는 모습: 활동이 비슷해지자 권태로 떠남(F110) / 일회성 만남 뒤의 허무함(F055) / 출석 맞추기가 가장 어려움(F063)
- 잘 될 때 신호: 오랜만에 와도 반가워함(F017, F018), 공백 후 복귀율, 일회성 참여자가 정기 참여자로 바뀜
- 설계 긴장: **자유로운 참여 ↔ 정해진 리듬** / **가벼움 ↔ 소속감** (01번 핵심 모순)
- 디지털 제품과 다른 점: 앱은 알림과 습관으로 리텐션을 끌어오지만, 모임은 삶의 10%라서(F026) 의무를 늘리면 떠난다

### H8 바깥 서열이 없는 평평함
- 설명: 직장·나이·실력의 서열과 오래된 사람끼리의 벽이 모임 안에 다시 생기지 않아야 한다
- 점검 질문
  - 모임 안에서 나이, 직업, 실력에 따른 서열이 느껴지는가?
  - 말을 많이 하는 사람과 거의 못 하는 사람이 정해져 있지 않은가?
  - 오래된 사람끼리만 아는 말과 무리가 새 사람을 밀어내고 있지 않은가?
  - 모임이 커지면서 경험이 들쑥날쑥해지고 있지 않은가?
- 어기면 보이는 모습: 토론을 좌지우지하는 사람 때문에 직장 위계를 다시 겪어 탈퇴(F012) / 승부 집착(F074) / 실수를 질책하며 패가 갈림(F081) / 내부자 용어(F121) / "아무나 온다"며 초기 회원 이탈(F008)
- 잘 될 때 신호: 직업과 신분이 드러나지 않는 평등한 자리(F105), 신규와 기존 구성원이 섞임, 발언이 고루 나뉨
- 설계 긴장: **소속감 ↔ 배타성** / 성장 ↔ 경험의 질
- 디지털 제품과 다른 점: 제품의 사용자는 서로를 거의 의식하지 않지만, 모임에서는 다른 구성원이 곧 경험의 질이다

### H9 나눠 맡는 운영
- 설명: 더 하고 싶은 사람이 맡을 자리가 있고, 운영과 갈등 조정이 한 사람에게 몰리지 않아야 한다
- 점검 질문
  - 조금 더 하고 싶은 사람이 맡을 수 있는 작은 일이 있는가?
  - 운영자가 한 달 빠지면 모임이 돌아가는가?
  - 갈등이 생기면 누가, 어떤 방식으로 다루는가?
  - 기여하지 못하는 사람이 미안해하고 있지 않은가?
- 어기면 보이는 모습: 주도하는 사람이 없으면 흐지부지(F056) / 대표에게 몰려 소진과 갈등(F064, F065) / 수평적이라 조정할 사람이 없어 쉽게 돌아섬(F094) / 봉사하지 못한 사람의 죄책감(F119)
- 잘 될 때 신호: 역할을 맡은 구성원 수, 뒤따르던 사람이 앞장섬(F092), 받은 도움을 돌려줌(F118), 힘이 회원 모두에게 나뉨(F067)
- 설계 긴장: 운영자 주도 ↔ 구성원 자율 / 기여의 기회 ↔ 기여의 압박
- 디지털 제품과 다른 점: 제품은 출시 뒤에도 만든 쪽이 운영하지만, 모임은 구성원이 운영을 나눠 맡아야 지속된다

### H10 열려 있는 떠남과 돌아옴
- 설명: 떠나는 것은 자연스러운 일로 받아들이고, 떠난 사람이 다시 돌아올 길이 남아 있어야 한다
- 점검 질문
  - 사람들은 왜 떠나는가? 그 이유를 알고 있는가?
  - 정회원이 아니어도 가끔 참여할 수 있는 길이 있는가?
  - 떠난 사람이 다시 오고 싶을 때 어색하지 않게 돌아올 수 있는가?
- 어기면 보이는 모습: 흥미를 잃고 떠남(F050) / 떠난 사람 6명 모두 2~3년 안에 다시 가입하지 않겠다고 답함(F076) / 호기심에 왔다가 그만둠(F090)
- 잘 될 때 신호: 떠난 사람도 맞는 곳이면 다시 하고 싶어 함(F084), 소속 없이 시간 날 때 참여하는 길(F085), 복귀율
- 설계 긴장: 붙잡기 ↔ 잘 보내기 / 정회원 ↔ 느슨한 참여자
- 디지털 제품과 다른 점: 제품은 이탈을 막아야 할 실패로 보지만, 모임에서 떠남은 삶의 자연스러운 일부이고 돌아올 수 있는 관계로 남길 수 있다

## 4. 접점 층: 온·오프라인 접점 (구 P10)
- 위치: 휴리스틱이 아니라 **모든 휴리스틱을 어디서 점검할지 정하는 층**. 디자이너에게 익숙한 화면은 관계를 잇는 접점 중 하나일 뿐이라는 관점(31번 P10)을 구조로 드러냄
- 근거: 온라인은 가벼운 대화·정보로 오프라인을 보완(F024), 온라인 연락 + 월 1회 만남(F025), SNS 기록과 오프라인을 오가며 신뢰 갱신(F021), 온라인 카페는 관리해야 유지(F103), 온라인 인정이 참여로(F107), 카톡방 오해가 갈등(F066), 친밀감은 오프라인에서(F007)

## 5. 쓰는 방법 (두 겹)
### 누구나 겹: 점검
- 운영자가 혼자, 또는 구성원 몇 명과 함께 점검 질문에 답해 봄
- 답이 "아니요"이거나 "모르겠다"인 휴리스틱이 다음에 살펴볼 곳

### 디자이너 겹: 휴리스틱 평가 (Nielsen 방식을 모임에 맞게)
1. 평가자 3~5명: 운영자, 오래된 구성원, 최근에 온 구성원, 바깥 사람(디자이너)을 섞음 (Nielsen은 평가자 3~5명 권장, 원문 확인)
2. 각자 최근 모임 한 번의 여정(모임 전 → 현장 → 직후 → 모임 사이)을 떠올리며 휴리스틱별 문제를 적음
3. 문제마다 심각도를 매김

| 심각도 | 뜻 |
|---|---|
| 0 | 문제 아님 |
| 1 | 불편하지만 참여에는 영향 없음 |
| 2 | 일부 사람이 망설이거나 덜 참여하게 됨 |
| 3 | 일부 사람이 다시 오지 않게 됨 |
| 4 | 많은 사람이 떠나거나 모임이 멈출 수 있음 |

4. 심각도 높은 문제부터 작은 실험으로 고쳐 보고, 잘 될 때 신호로 확인 (30번 작은 실험)

## 6. 프레임워크 전체 구조 (휴리스틱은 그 중심)
- 휴리스틱 = 프레임워크 전부가 아니라 개념의 핵심. Jabareen(2009)의 "서로 연결된 개념들의 망"이 되려면 연결 구조가 필요
- 구조 v0 (FigJam "프레임워크 구조 v0" 섹션에 그림)
  - ① 관점: 사용자 ↔ 시스템에서 사용자 ↔ 사용자로. 다른 점 네 가지(관계·현장·지속 운영·의도된 마찰)
  - ② 휴리스틱 10개: 무엇을 보나
  - ③ 구성원 여정(시작하기 → 진입 → 첫 경험 → 관계 맺기 → 지속 → 함께 운영 → 떠남과 돌아옴)과 접점 층(모임 전·현장·직후·모임 사이): 언제·어디서 보나
  - ④ 설계 긴장: 무엇 사이에서 고민하나
  - ⑤ 신호와 작은 실험: 점검 → 심각도 → 작은 실험 → 신호 확인의 순환
  - 두 겹: 누구나 겹(②④) / 디자이너 겹(③⑤)
- 다른 프레임워크와의 차이: Community Canvas는 질문 목록(②에 해당)은 있지만 ③④⑤가 없음 → 강점으로 6단계 비교에 사용 (연구자 해석)
- 이름: "Community ___" 미정. 구조를 보고 결정
